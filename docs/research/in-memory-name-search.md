# In-memory item-name search

Research dates: August 2026. Measurements are from Node 24 probes on the 12-locale catalog; they explain the design but are not guarantees.

## What search promises

`searchItems(query, locale, first)` returns every item whose name in `locale` contains the query, after both are folded the same way. It is exact: no typo correction, stemming, transliteration or semantic matching.

Folding, applied to names at build time and to the query once per search:

1. trim surrounding whitespace;
2. normalize with NFKC and lowercase using the locale's BCP 47 tag (so Turkish dotted and dotless i behave correctly);
3. decompose with NFKD and drop combining marks whose base character is Latin (so `epee` matches `Épée`, while Thai marks and Japanese dakuten stay);
4. remove all whitespace and punctuation, keep numbers and symbols such as `+`.

Examples in English: `blackstone` finds "Black Stone", `chiros` finds "Chiro's", `Advance` finds "Epheria Carrack: Advance (Chiro's Cannon)", and `shiro` does not find "Chiro".

Queries must be at least 3 code points after folding and no longer than the longest folded name. `first` is 1 to 100 (default 50). Results are ordered exact match, then prefix, then other substring matches, with ties broken by folded name and item ID. There is no cursor: refine the query when `totalCount` exceeds what you got back. Search responses are cached like any other answer: `Query.searchItems` alone keeps the catalog's long window, since names change only with a release, and a search that also selects `marketSummary` takes the shorter price window. A deployer who expects many single-use query strings can add `Query.searchItems` to `CACHE_NEVER_STORED`.

## Design

One immutable artifact, generated by `moon run catalog-tools:generate` and bundled into the catalog Worker, holds for all 12 locales:

- item IDs and grades, aligned across locales;
- display names and folded search keys;
- a compact trigram index per locale: sorted gram strings, a `Uint32Array` of offsets, and a flat `Uint32Array` of item positions.

For a folded query of 3 or more code points the search:

1. produces the query's distinct trigrams;
2. binary-searches each in the locale's gram list, returning nothing at once if any is missing;
3. takes the shortest posting list as the candidate set;
4. keeps only candidates whose search key `includes` the query;
5. sorts, counts and slices.

Step 3 is complete because every true match contains every query trigram; step 4 removes false positives. The Worker never builds an index at request time and holds no mutable cache, so concurrent requests can share the data safely.

## Why this and not a library

The catalog is 12,508 names per locale, 150,096 in total. Search is always within one locale.

| Approach (exact substring)               | Correct | Latency                                   | Extra memory |   Artifact (raw / gzip) |
| ---------------------------------------- | ------- | ----------------------------------------- | -----------: | ----------------------: |
| Normalized linear scan                   | yes     | 0.37 ms mean, 0.71 ms p95                 |         none | 5.4 / 0.7 MiB (catalog) |
| Compact bigram + `includes`              | yes     | 0.051 ms mean, 0.15 ms p95 (2+ chars)     |     13.5 MiB |          16.2 / 6.1 MiB |
| **Compact trigram + `includes`**         | **yes** | **0.039 ms mean, 0.11 ms p95 (3+ chars)** | **16.4 MiB** |      **17.2 / 6.5 MiB** |
| Bigram + trigram                         | yes     | 0.041 ms mean, 0.13 ms p95                |     30.0 MiB |         33.4 / 12.6 MiB |
| FlexSearch `full` tokenizer + `includes` | no      | 0.26 ms mean, 0.84 ms p95                 |      306 MiB |         59.4 / 12.3 MiB |

- The trigram index was chosen: fastest, exact, and within Cloudflare's Worker limits (128 MB isolate memory, 10 MB compressed upload on the paid plan). The bigram-plus-trigram variant exceeds the compressed upload limit on its own.
- FlexSearch's all-substring index alone exceeded the isolate memory limit and still missed queries spanning spaces and punctuation, because its tokenizer splits on them.
- Fuzzy and ranked libraries were compared for a possible typo-tolerant future: MiniSearch (an inverted index with prefix and edit-distance search, serializable to JSON) was the best fit, with uFuzzy as the strongest no-index alternative. Fuse.js was too slow at this size (about 32 ms mean), fuzzysort missed middle-substring cases, and Orama brought much more than needed. None of them guarantees arbitrary substring matches, so exact search does not use them.
- Two runtime facts rule out some library features anyway: Workers are single-threaded with no Web Worker API, and they forbid `eval`/`new Function`, which FlexSearch's fast-boot import relies on.

## Vectors

Semantic search does not fit in a Worker's memory: one 1,024-dimension float32 vector per localized name is about 586 MiB before any index. A hosted vector index (such as Cloudflare Vectorize) with a query embedding could add concept search later, behind the exact results and only for submitted searches. Exact names do not need it.

## If typo tolerance is ever added

Keep the exact tiers first (exact name, prefix, word match, substring), add edit-distance-1 matches only for terms of four or more characters and rank them last, build any per-locale index lazily with a small cap on how many stay in memory, and measure memory and first-query time in `workerd` before shipping.
